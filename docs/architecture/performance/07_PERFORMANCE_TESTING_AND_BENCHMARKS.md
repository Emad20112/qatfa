## 1. المقدمة والأهداف الهندسية (Testing Philosophy)

لا يمكن اعتبار أي قرار معماري ناجحاً ما لم يخضع للقياس التجريبي والتحقق الصارم تحت أعباء تحاكي الواقع الفعلي. تهدف هذه الوثيقة إلى وضع إطار متكامل لاختبارات الأداء، ومقاييس الجودة المعيارية (SLA Benchmarks)، واختبارات التحمل والضغط (Load & Stress Testing) لمنصة **قطفة (Qatfa)** عبر كافة طبقاتها:
1. **قاعدة البيانات (PostgreSQL 16 & PostGIS):** قياس أزمنة الاستعلام، ومعدل المعاملات بالثانية (TPS)، واستهلاك الذاكرة ومجمع الاتصالات.
2. **طبقة الخدمات والـ API (NestJS/Fastify & Redis):** فحص قدرة الخادم على خدمة آلاف الطلبات المتزامنة في ساعات الذروة (11:30 ص - 4:30 م) ورصد زمن الوصول P95 و P99.
3. **تطبيق الموبايل (Flutter Client):** قياس معدل الإطارات (60 FPS)، وزمن بدء التشغيل (Cold Start)، وسلوك الذاكرة على الهواتف الاقتصادية (2GB RAM).
4. **كفاءة الشبكة ونقل البيانات:** قياس استهلاك البايتات الفعلية المنقولة عبر شبكات 3G واختبار محاكاة فقدان الحزم.

## 2. اختبارات ومقاييس قاعدة البيانات (Database Benchmarks & EXPLAIN Verification)

### 2.1 سيناريوهات فحص الضغط عبر أداة `pgbench`
تم تصميم 3 نصوص اختبارية مخصصة لأداة `pgbench` تعكس الأنماط الحقيقية لاستعلامات سوق القات:

```bash
# تشغيل اختبار ضغط التصفح والبحث بالميزانية لمحاكاة ذروة 150 عميلاً متزامناً
pgbench -h localhost -p 6432 -U qatfa_user -d qatfa_db \
        -c 150 -j 8 -T 120 -P 5 \
        -f bench_budget_search.sql
```

#### نص اختبار البحث العكسي بالميزانية (`bench_budget_search.sql`):
```sql
\set budget random(5000, 30000)
\set market_id random(1, 25)
SELECT p.id, p.title, p.price, ABS(p.price - :budget) AS delta
FROM products p
WHERE p.is_active = TRUE 
  AND p.stock_status = 'AVAILABLE'
  AND p.drop_date = CURRENT_DATE
  AND p.market_id = :market_id
  AND p.price BETWEEN (:budget * 0.9) AND (:budget * 1.1)
ORDER BY delta ASC, p.created_at DESC
LIMIT 20;
```

## 3. اختبارات حمل وخوادم الـ API (API Load & Concurrency Testing)

### 3.1 سيناريو اختبار الحمل المعتمد بأداة `k6`
تم إعداد سكريبت فحص حمل احترافي بأداة **k6** يحاكي تصاعد حركة المستخدمين في نافذة الذروة (11:30 ص إلى 4:30 م):

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 500 },   // تصاعد مبكر لحركة الدخول
    { duration: '5m', target: 2500 },  // نافذة الذروة (2,500 مستخدم متزامن)
    { duration: '2m', target: 5000 },  // ذروة استثنائية (5,000 مستخدم متزامن)
    { duration: '2m', target: 0 },     // انحسار الحركة
  ],
  thresholds: {
    http_req_duration: ['p(95)<150', 'p(99)<250'], // 95% من الطلبات أقل من 150ms
    http_req_failed: ['rate<0.001'],               // نسبة أخطاء أقل من 0.1%
  },
};

export default function () {
  const params = {
    headers: {
      'Accept-Encoding': 'br, gzip',
      'Accept': 'application/json',
    },
  };

  // 1. تصفح موجز الصفحة الرئيسية بالمؤشر
  let feedRes = http.get('https://api.qatfa.ye/api/v1/products/drops?marketId=12&limit=20', params);
  check(feedRes, {
    'Feed Status 200': (r) => r.status === 200,
    'Brotli Compressed': (r) => r.headers['Content-Encoding'] === 'br',
  });

  sleep(1);

  // 2. البحث بالميزانية
  let budgetRes = http.get('https://api.qatfa.ye/api/v1/products/search?targetBudget=15000&tolerance=0.10&marketId=12', params);
  check(budgetRes, {
    'Budget Status 200': (r) => r.status === 200,
    'Fast Response': (r) => r.timings.duration < 150,
  });

  sleep(2);
}
```

## 4. اختبارات أداء تطبيق Flutter والذاكرة (Client Profiling & SLAs)

### 4.1 قياس معدل الإطارات وسلاسة التمرير (Frame Rendering Profiling)
- **أداة الفحص:** Flutter DevTools Performance Overlay & Timeline Trace.
- **جهاز الفحص المرجعي:** هاتف اقتصادي (Tecno Spark 8C / Android 11 / 2GB RAM).
- **سيناريو الفحص:** التمرير المستمر بأقصى سرعة (Fling Scroll) عبر 300 بطاقة عرض في شاشة موجز القطفات اليومية تحت إضاءة ساطعة.
- **المعايير المعتمدة:**
  - ثبات معدل الإطارات عند **60 FPS**.
  - زمن معالجة الإطار (Frame Build & Raster Time) $\le 12.5\text{ ms}$ (سقف أمان دون حاجز الـ 16.6ms).
  - نسبة الإطارات المتأخرة (Jank Frames) **$\le 0.8\%$** من إجمالي إطارات جلسة التمرير.

### 4.2 قياس زمن بدء تشغيل التطبيق (Cold Start Profiling)
- **التعريف:** الزمن المستغرق من لحظة نقر المستخدم على أيقونة «قطفة» في هاتف أندرويد وحتى اكتمال رسم أول بطاقة قطفة حية على الشاشة (First Meaningful Paint).
- **الهدف الهندسي:** $\le 1.2\text{ ثانية}$ على الأجهزة المتوسطة، و $\le 1.8\text{ ثانية}$ على الأجهزة الاقتصادية القديمة (Android 8.0).

### 4.3 فحص تسريب الذاكرة وسلوك الـ OOM (Memory Leak Profiling)
- **أداة الفحص:** DevTools Memory Snapshot & Android Studio Memory Profiler.
- **إجراء الفحص:**
  1. فتح التطبيق والتمرير عبر 200 بطاقة عرض متتالية.
  2. الدخول إلى 30 شاشة تفاصيل لقطفات مختلفة والرجوع منها.
  3. تشغيل 15 مقطع فيديو إعلاني قصير وإيقافها.
  4. التقاط صورة بالكاميرا وتوليد ملف WebP بالخلفية.
  5. تكرار هذه الدورة 10 مرات متتالية لمراقبة منحنى نمو الذاكرة (Memory Growth Slope).
- **معيار القبول الصارم:**
  - يجب ألا يتجاوز إجمالي استهلاك الذاكرة في ذروة النشاط حاجز **95 ميجابايت**.
  - بعد ترك التطبيق خاملاً لمدة 5 ثوانٍ، يجب أن يستقر استهلاك الذاكرة العشوائية دون أي نمو تصاعدي (Flat Memory Curve) مما يؤكد نجاح الـ Garbage Collector في تحرير كائنات الصور ومتحكمات الفيديو.

## 5. اختبارات كفاءة باقات البيانات والشبكات الضعيفة (Network Benchmarking)

### 5.1 قياس حمولة البيانات المنقولة (Wire Size Transfer)
تم استخدام أدوات تحليل الحزم (Charles Proxy / Wireshark) لقياس حجم البيانات المنقولة في جلسة تصفح واقعية:

| الإجراء الميداني | الحجم المنقول قبل التحسين | الحجم المنقول بعد التحسين المعماري | نسبة التوفير في باقة المستخدم |
| :--- | :--- | :--- | :--- |
| **فتح التطبيق وجلب أول 20 بطاقة** | 84.5 KB (JSON) + 2.4 MB (صور) | **3.1 KB** (JSON) + **280 KB** (WebP) | **توفير بنسبة 88.6%** |
| **التمرير الإضافي لـ 80 بطاقة** | 338.0 KB (JSON) + 9.6 MB (صور) | **12.4 KB** (JSON) + **1.1 MB** (WebP) | **توفير بنسبة 88.8%** |
| **تحديث الشاشة بالسحب (304 Cache)** | 84.5 KB (إعادة تحميل كاملة) | **0.0 KB** (استجابة مشروطة 304) | **توفير بنسبة 100%** |
| **رفع صورة قطفة جديدة بواسطة المقاوتي**| 4.8 MB (صورة الكاميرا الأصلية) | **88 KB** (WebP 75% عبر Isolate) | **توفير بنسبة 98.1%** |

### 5.2 اختبار محاكاة الشبكات الخلوية المتدهورة (Network Chaos Testing)
تمت محاكاة ظروف الاتصال الرديئة في بعض مناطق الأرياف وأسواق القات الجبلية:
- **معدل تأخير (Latency):** ضبط التأخير على **450 ms**.
- **معدل فقدان الحزم (Packet Loss):** ضبط الفقدان على **8%**.
- **معدل عرض النطاق (Bandwidth):** خنق السرعة عند **128 Kbps (2G/Edge)**.
- **معايير القبول:**
  1. صمود التطبيق وعدم تجميد واجهة المستخدم نهائياً (No UI Freezes).
  2. إظهار هياكل التحميل (Shimmer/BlurHash) فورياً دون ترك مساحات بيضاء.
  3. نجاح بروتوكول إعادة المحاولة بالخلفية (`RetryInterceptor`) في إتمام الطلبات بنسبة تتجاوز **99%**.
  4. ظهور الشريط التنبيهي الأصفر بوضوح عند انقطاع الاتصال التام مع استبقاء آخر بيانات.
